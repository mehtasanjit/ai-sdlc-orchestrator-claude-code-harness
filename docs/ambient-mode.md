# Zero-touch — workflows from plain words, and hand-off mode

> This is the full reference. For zero-touch in plain words, with five scenarios to try, see the [zero-touch guide](zero-touch-guide.md).

Zero-touch is the part of the plugin that works while you chat with Claude Code as usual. It is switched by its own plugin, **`zero-touch`**, listed beside `mmo` in the same marketplace: install and enable it and new chats have zero-touch; disable it and no chat has any (zero-touch's workflow and hand-off hooks are registered by the zero-touch plugin itself, so Claude Code does not run them for a disabled plugin). Without it no zero-touch hook acts, and the `mmo` plugin runs its `/mmo:` commands and nothing else.

It has two modes, and an Off setting, all chosen in the chat (below):

- **Workflow mode** (Workflows): you type a normal sentence; if it clearly asks for one of the eight `/mmo:` jobs, that job's workflow runs exactly as if you had typed the command, on the models you chose. Every other message is an ordinary Claude Code chat.
- **Hand-off mode** (Hand-off): the chat's own model does the development, and new documents, specs, plans, tests and one change repeated in many files go to the model you chose for that kind of work, and are checked before they reach your project. It has its own section, "Hand-off mode", below; everything before that section describes workflow mode unless it says otherwise.
- **Off**: the plugin stays installed, and Claude works as normal.

(The file keeps the name `ambient-mode.md`, so existing links still work.)

## Choosing: the settings box, in the chat

A person sets zero-touch up only in the chat, in Claude Code's own question box (the `AskUserQuestion` tool), never by editing a file or typing a command. It is the one picker a plugin can put in front of a person in the desktop app and the terminal alike: the desktop app has no plugin settings form, and it declines an MCP server's pop-up form.

- **The first chat after install** asks before anything else. The welcome says so (in the terminal at the chat's start; in the desktop app with the first message, where Claude also writes it in one short paragraph just before the box, because the app shows it only as a collapsed notice); Claude opens the box. If Claude tries a tool that changes anything before the box has been shown, that one call is refused once, with the box in the reason and a way out where the box cannot be shown; after that nothing is held in that chat. The wait lasts about one turn: if the box was never shown by the person's next message typed while the chat is idle (Claude did not open it, or the question tool is not available there), zero-touch gives up in that chat and says so, and the next new chat asks again. A message the transcript does not show yet (possibly typed mid-turn) is not taken as a new turn; after three messages the hold ends anyway, so nothing is held for ever. Settings saved meanwhile in another chat end a waiting first chat's questions and hold at once; that chat carries on without zero-touch, like any open chat, and says so. The answers apply to that chat at once. After choosing Workflows, the first message (which arrived before zero-touch had settings) is judged without being sent again: zero-touch's message hook keeps it, the settings box leaves it in the chat's folder (`zt_replay.json`), and mmo's end-of-turn hook judges it once with the same rules as a typed message. A job: the turn continues with its start instruction (the Stop hook's `additionalContext`, as a queued job starts) and the person sees the start line; a start Claude then does not make is dropped and said; when something the settings need is missing, the saved line says the job can start in a new chat once it is fixed. Anything else: Claude answers it. With workflows switched off by a setting file, or mmo not usable, Claude answers it at once and the saved line says why; with the chat on another model than the person's workflow models plan with, it is not judged (see "The chat's model"). A typed `/mmo:` workflow command as the first message runs as typed, and zero-touch steps out of that chat (`Zero-touch: your command runs as you typed it. Zero-touch won't do anything in this chat; it will ask for its settings in your next new chat.`); any other command typed as the first message is asked for again. The first chat's Hand-off questions say "starting with this chat", and a choice typed by hand is understood whatever its capitals, spaces or hyphens.
- **Any later chat, in any mode, Off included:** the person types `change zero-touch settings` (any wording that names zero-touch works: Claude understands it and only opens the box; every choice is a click). A message that names zero-touch (`zero-touch`, `zero touch`, `zerotouch`; the same rule as mmo's routing, `zero-touch/scripts/prompt-kind.mjs` `mentionsZeroTouch`) gets Claude two things from zero-touch's message hook: this chat's facts (its mode and models, set when it started, and what is saved for new chats; so "is zero-touch on here?" gets a true answer, never a guess) and the exact box. They come only then, not at every chat's start: a chat that never mentions zero-touch carries none of it, and a chat opened before zero-touch was installed, or loaded into an open chat with `/reload-plugins`, gets them too.
- **Always the same order:** the mode question (Workflows / Hand-off / Off); after Workflows, the models question (Opus 5 + Flash 3.8, Fable 5.1 + Flash 3.8, Opus 5 + Sonnet 5, Opus 5 only: the shipped policies `opus-plus-flash-v38`, `fable51-plus-flash-v38`, `opus-plus-sonnet`, `opus-only-v5`; four is the most the question box shows; Fable 5.1 + Flash 3.8 plans with Fable 5.1, so its chat is on Fable 5.1); after Hand-off, four questions in one box: the chat model (Opus 5, recommended, or Sonnet 5), and who writes new documents, specs and plans; new tests; and one change repeated across many files (Flash 3.8, Sonnet 5, or Keep in chat). Off needs nothing more.
- **The choice in force is marked** "(your current choice)". The other mode's choices are kept when the mode changes.
- **Money is said as who runs each model, never as a price rank.** Most people sign in to Claude with a plan, where Opus 5 and Sonnet 5 use the plan's limits and Flash 3.8 is billed by Google, so "the cheapest" could mean a new bill. The boxes say how much of the person's Claude usage a choice takes and that Flash 3.8 runs on their Google account (`Uses the least of your Claude usage; Flash 3.8 runs on your Google account.` / `Everything runs on your Claude account.` / `Uses the most of your Claude usage.`), which is true on a plan and with an API key alike; the start messages make no price claim; a hand-off receipt's dollar figure is called an estimate (`Estimated cost: $0.0041`), the models' list price for the tokens used. Test: `tools/test/zero-touch-cost-words.test.mjs`.
- **What starts a workflow is said as what is recognised:** `Ask for a job in English, starting with what you want done and saying what it is about (fix the login bug, build a to-do app…)`, and in the start message `When you ask in English for one of these jobs, starting with what you want done and saying what it is about (for example "fix the login bug", "add a due date to the to-do form", or "build a small to-do app" in an empty folder)`. A request in another language, or one that only describes a problem, gets a normal answer, with no line; and a change must say what it is about, because recognition is precision first (`add a due date to each to-do` names no part of the project and is answered as chat). Every example given is routed by a test. The start message's own job words are recognised too: `clean up …` / `tidy up …` (refactor, when it names something in the software), `upgrade the lodash library` / `bump the axios package` (deps: only those two verbs, a named package, then library / package / dependency and at most a target version), and `add X to the Y feature` (feature-extend). Tests: `tools/test/ambient-route.test.mjs`, `tools/test/zero-touch-cost-words.test.mjs`.
- **All or nothing:** the settings are saved only when the sequence is complete. An answer typed in the box's "Other" line saves nothing and says so. A closed box reaches no hook, so it is noticed at the person's next message, and only at a message the transcript shows as typed while the chat was idle: a notice Claude Code queues, a message typed while Claude works, or one the transcript does not show yet, never ends a sequence that is half done (`zero-touch/scripts/prompt-kind.mjs`, a copy of mmo's own rule, kept identical by `tools/test/zero-touch-prompt-kind.test.mjs`).
- **What is saved reaches new chats** (a new chat in the desktop app; in the terminal, a restart or `/clear`, which Claude Code gives a new chat id). An open chat keeps what it started with.
- **Enforced, not trusted:** a zero-touch box that is not exactly the one expected now is replaced by the exact one before it is shown (the hook's `updatedInput`). A box counts as a zero-touch box when it names zero-touch AND offers a settings choice (a mode, a model, keeping work in the chat); every other box (Claude's own questions, one that merely mentions zero-touch, a workflow's approval step) is never touched. The rule is lexical, so a question of Claude's own that names zero-touch and offers such a word ("Which zero-touch mode should the README explain first?" with "Workflows first") is still caught, and the settings box is shown in its place: an accepted limit, rare, and never stuck. Every box a note gives Claude (when the person names zero-touch, in the first chat, after a save, after a closed box) is built by the one rule the check uses (`settings.mjs` `boxCurrent`), so Claude's first try is the right one. A helper agent never opens the settings.

**Settings that cannot be used fail safe**, so a damaged or hand-edited file never switches anyone to paid workflows. A file that cannot be read, is larger than 16 KB, or holds any value that is not one of the box's choices (the mode is required; another value may be left out and then takes the standard one), is not used at all; zero-touch, mmo's hooks (`lib/zt-saved.mjs`) and the model server (`handoff/listing.ts`) all read it by this one rule. Every save also writes `settings.last-good.json` beside it; when the file cannot be used, that last good save is in force, and every chat says so (`Zero-touch couldn't read your settings file, so it's using the last settings you saved: …`). With no last good save, zero-touch is Off in new chats and every chat says `Zero-touch couldn't read your settings, so it's off in this chat. To choose them again, type "change zero-touch settings".` The lines after a box never call the standard settings the person's ("Your settings still can't be read, so zero-touch stays off in new chats."). A save that fails (a full disk, a folder zero-touch may not write) changes nothing and says so with the cause in plain words, and Claude is told it was not saved; in the first chat that chat then stays without zero-touch.

The settings live in the zero-touch plugin's own data folder, `${CLAUDE_PLUGIN_DATA}/settings.json` (Claude Code keeps it across updates and deletes it when the plugin is removed; without that variable, `~/.mmo-ambient/zero-touch/`). Code: `zero-touch/scripts/settings.mjs` (the file), `boxes.mjs` (the boxes, word for word), `settings-hook.mjs` (the hooks around the box), `messages.mjs` (every text the plugin shows). Tests: `tools/test/zero-touch-settings.test.mjs`, `zero-touch-settings-box.test.mjs`.

**The rule for models: the person's pick, or the standard one, nothing else.** A project's own `routing-policy.yaml` and its saved choice in `.sdlc/project.json` are not used by zero-touch (the start lines say so in every chat in a folder that has such a file). A `/mmo:` command the person types keeps following them.

## Turn it on and off

| How | Effect |
|---|---|
| Install the `zero-touch` plugin (`/plugin install zero-touch@tilicho-ai-labs` in a terminal chat, or the plugin browser in the desktop app; Claude Code installs and enables `mmo` with it) and leave it enabled | New chats have zero-touch; the first one asks for the settings. |
| Choose Off in the settings box | New chats have no zero-touch work and say nothing (the saved line confirmed the choice); the settings box still works in them. Open and reopened chats let go too, at their next message: `Zero-touch: you turned zero-touch off in its settings, so this chat works as normal from here.` (a workflow already running in a chat finishes first). The chat where Off is chosen is told by its saved line instead: `Zero-touch: your settings are saved: Off. Zero-touch stops in this chat from your next message (a workflow already running here finishes first), and new chats start without it.` Every other change of the settings reaches new chats only. |
| Disable it in Claude Code's plugin list (desktop: **+** next to the prompt box → **Plugins** → **Manage plugins**; terminal chat: `/plugin` → **Installed**; shell: `claude plugin disable zero-touch@tilicho-ai-labs`) | No chat has any zero-touch work once Claude Code reloads its plugins (a new chat, a restart, `/reload-plugins`), reopened ones included, and nothing is shown. The `/mmo:` workflows are untouched: they are the `mmo` plugin. Claude Code refuses to disable `mmo` while `zero-touch` needs it (documented for the terminal). |
| Remove it completely | In a terminal: `claude plugin uninstall zero-touch@tilicho-ai-labs --prune`, which also removes `mmo` when nothing else needs it (it was installed as zero-touch's dependency) and deletes zero-touch's settings. Zero-touch's chat records under `~/.mmo-ambient` age out (30 days) or can be deleted by hand. |
| `MMO_AMBIENT=on` or `MMO_AMBIENT=observe` in the environment | For one run, without the settings: a developer or a measuring setup. `on` is workflow mode on the person's workflow models; `observe` records the chat's events and starts nothing. |
| `MMO_AMBIENT=off` | Off for this run, plugin or not. |

**The person sees it.** Zero-touch's messages come from its own code, as a hook's `systemMessage`: Claude Code shows it to the person and does not give it to the model, so the model cannot reword it. Where it shows depends on the screen: the terminal shows every hook's line in the chat; the desktop app folds a message or tool hook's line into a collapsed "Claude Code notice", and does not show a start hook's line at all (see the start lines below). A person may never open a folded notice and read only Claude's reply, so outside the terminal (`lib/relay.mjs`, zero-touch's copy `zero-touch/scripts/relay.mjs`), a line the person must act on is also given to Claude with the instruction to start its reply with it, word for word: every line at a message or a tool call, a save with something to act on, and a start line that is a warning. A refusal is shown in red already and is left alone, and a line at the end of a turn is never given to Claude on its own (that would start a new turn of the model just to repeat it). Claude is asked, not forced: it may word it differently. The words are written for someone with no context and no technical knowledge.

- **The start lines**, from the zero-touch plugin's start hook (`zero-touch/scripts/start-chat.mjs`), quiet by default:
  - **The summary, once per save:** which mode is on, what to ask for, which models run, what a workflow costs and asks, how to change it. It shows in the first new chat after the settings are saved (`settings.mjs` `summaryShown`, a record of the save it was shown for: its time and what it holds), and counts as shown only once a person could have seen it.
  - **After that, only what needs the person's action, in every chat:** Google is not connected and the models need it (see "Google" below), the Hand-off chat is known to be on another model than it needs, the settings file could not be used and the last good save is in force (see "Settings that cannot be used" above), the folder has its own `routing-policy.yaml` (not used by zero-touch). The mode in one line, then those lines (`messages.mjs` `warningsMessage`). Nothing at all when nothing needs action.
  - **Off says nothing** (the saved line confirmed it), never checks or updates mmo, and leaves nothing behind. **A compaction or a reopened chat shows nothing again**; Claude gets back what a compaction drops (a Hand-off chat's rules, the first chat's note to open the box).
  - **Where:** the terminal shows a start hook's line at the top of the chat, so the lines go there at once. The desktop app does not show it at all, so everywhere but the terminal (a screen label this code does not know included) the lines wait in the chat's folder (`zt_say.json`) and the message hook shows them once, with the chat's first message; a notice Claude Code queues does not use them up (`mark.mjs` `startMessageShown`). A run with no person at a screen (a script's `claude -p`, the Agent SDK, a `claude -p` started from inside a chat, which Claude Code marks unattended) is left exactly as Claude Code alone: nothing marked and nothing said (`mark.mjs` `noScreen`).
  - **mmo switched off, missing or too old.** The start hook reads Claude Code's own records the way Claude Code decides: the first settings file that names mmo (the organisation's, then the project's local file, then the project's, then the person's) says whether it is on, and an mmo older than zero-touch needs (its `scripts/ambient/api.json` carries the version of the zero-touch hooks it holds; an mmo without that file holds none) counts as too old. Then no chat is marked, the person reads `Zero-touch can't work right now, because a plugin it needs, mmo, is switched off or missing. …` (or `… is an older version. Update mmo in your plugins list, then start a new chat.`), with the first message on the desktop app, and Claude is told not to open the settings box. A save made meanwhile names the missing piece instead of promising a mode. **Too old is fixed by zero-touch itself** (`zero-touch/scripts/mmo-update.mjs`): Claude Code installs a missing dependency with zero-touch but leaves an installed one at its version (with or without a version range in the manifest), so the first chat that finds mmo too old starts Claude Code's own `claude plugin update mmo@<marketplace> --scope <scope>` in the background (the install from zero-touch's own marketplace first, at the scope it was installed at; never an organisation's), and the person reads `Zero-touch is updating mmo, a plugin it needs, which is an older version. Claude works as normal in this chat. Start a new chat in a minute to use zero-touch.` (a save says `… zero-touch is updating it now. Start a new chat in a minute.`). One attempt at a time: another chat within ten minutes starts no second one; once an attempt is over and mmo is still too old, the manual words above are said. A switched-off mmo is "off", never "too old", so it is never overruled. The hook shim (`zero-touch/hooks/mmo-hook.sh`) and `mark.mjs` `mmoRoot` use only an mmo folder whose `scripts/ambient/api.json` says it carries zero-touch's hooks, so a copy in Claude Code's cache with the hook script but no `api.json` is never run. Tests: `tools/test/zero-touch-mmo-update.test.mjs`.
  - **Node.js missing or too old.** Without Node.js zero-touch cannot run: the shell scripts say so once per chat (in the terminal at the start, elsewhere with the first message, which every screen shows) and give Claude a note to answer normally and, if asked, point to nodejs.org. A Node.js older than 20 (mmo's floor) leaves the chat plain and is said the same way (`mark.mjs` `nodeTooOld`).
- **One line after each typed message**, from the prompt hook (`lib/route-flow.mjs` `PERSON_LINE`), always starting with `Zero-touch:`:

| What happened | Line |
|---|---|
| A recognised job starts | `Zero-touch: you asked for a bug fix, so Claude is starting the bug-fix workflow. It will wait for your approval at each main step.` |
| A queued job's turn comes (end of a turn) | `Zero-touch: the bug-fix workflow has finished, so the documentation workflow you queued is starting now.` |
| A workflow has ended (end of a turn) | Worded by how it ended: `Zero-touch: the bug-fix workflow has finished.` / `… was stopped.` / `… stopped because of a problem; Claude's last reply says what happened.` / `… stopped before it began.`, then `From here, asking for another job starts a new workflow; anything else gets a normal answer.` In a Hand-off chat (a typed workflow): `From here, Claude works in this chat in Hand-off mode again.` |
| The person types "stop" or "cancel" while a workflow runs | `Zero-touch: the bug-fix workflow was stopped, as you asked. Anything it already changed in your files stays as it is.` (plus `The workflow you had queued was dropped too.` when one was queued) |
| A start was announced but Claude never made it in that turn | `Zero-touch: the bug-fix workflow didn't start after all. Ask again to start it.` |
| This chat's workflow never began and sat waiting over 30 minutes, and another chat took the folder | `Zero-touch: the bug-fix workflow in this chat stopped before it began, because it waited more than 30 minutes and another chat in this folder has started a workflow since. Ask again here when that one has finished.` |
| A second job while a workflow runs | `Zero-touch: a bug-fix workflow is still running in this chat. In the box, choose whether the documentation workflow you asked for should wait its turn or replace the running one.` Then, after the answer: `queued. …`, `… was stopped, and … is starting now.`, or `nothing new was started; … carries on.` |
| A recognised job that cannot start | `Zero-touch: the bug-fix workflow didn't start, because …` with the real cause and what to do: another chat in this folder is running a workflow; Google is not connected; a change job in a project git does not track (`… isn't saved with git yet, and the workflow needs git so every change it makes can be undone. Ask Claude to "save this project with git", then ask again.`; Claude then runs `plugin/scripts/ambient/git-baseline.mjs` once, on the person's word), or no git on this computer; part of zero-touch is missing (reinstalling fixes it); the chat is on another model than the person's workflow models plan with (`… it needs this chat to be on Opus 5, and this chat is on Opus 5.5. Switch this chat to Opus 5 with the model menu next to the message box (in the terminal, type /model claude-opus-5), then ask again.`), or the person's own helper setting names another one; the start-up check took too long or failed. Never the check's raw output: Claude gets that. |
| A message that opens like one of the jobs (build, fix, add, write, …) but is none of them | `Zero-touch: this wasn't recognised as one of the jobs that get a full workflow, so Claude answers it normally. To start one, say what you want done and what it is about.` ("wasn't recognised as": "add a due date to each to-do" is a feature job said too loosely to start a paid workflow on) |
| A real job a folder rule declines | A new app asked for in a folder that holds a project: `… this looks like a new app, but this folder already holds a project, so no workflow was started. To build a new app, open an empty folder and ask there; to change this project, say what to add or fix.` A change asked for in a folder with no project, two jobs in one message, and a brief pasted into a project each get their own line with what to do. |

**A new app is saved with git.** Every change workflow refuses a folder git does not track (its rollback points are git commits), so a new-app run zero-touch started ends, once its run has completed, with zero-touch's end-of-turn hook saving the app with git, in code (`saveNewApp` in `plugin/scripts/ambient/hook.mjs`, running `plugin/scripts/ambient/git-baseline.mjs`; mmo's own command text is unchanged): `git init`, the files that must never be committed (dependencies, `.env` files, machine-local run records, logs) listed in git's own exclude file inside `.git` (no file of the person's is written), and one commit, "Starting point, before any changes" (with no git identity set on the computer, that one commit is signed "Zero-touch" and nothing is configured). A folder already in a git project, or a computer without git, is left as it is. The person's end line says what happened in one more sentence (`The new app is saved with git as a starting point, so the changes you ask for next can be undone.`; nothing more when it was saved already). A failed or stopped run is not saved, and a run started by typing `/mmo:greenfield` is left as mmo leaves it without zero-touch. Tests: `tools/test/zero-touch-git-start.test.mjs`.

**Quiet by default.** Nothing is shown for ordinary chat (a question, "thanks", a small edit such as a rename, an instruction that is not like a job), for a message while a workflow runs that is no new job or is the answer to its question, for a message about zero-touch itself ("change zero-touch settings": the zero-touch plugin handles it), for a message nobody typed (a machine notice), for a typed `/mmo:` command (the person named the workflow; only the Queue-or-Replace line can follow it), for a message sent while Claude is still working (it joins the running task), under `MMO_AMBIENT=off` or `observe`, or in a chat without zero-touch.

**The setup check.** The moment settings are saved, the saved line ends with what they need, checked on this computer: `Setup check: everything these settings need is ready on this computer.`, or `Setup check: one thing is missing on this computer.` (or two) with a line for each, saying what to do. What is checked: Google, when the models use Flash 3.8 (below); Claude Code's own command-line program, which every workflow and every hand-off of any kind runs (a new-app workflow's last attempt at every step; a Claude typist and every hand-off's last attempt): on PATH, else the Claude app's own newest copy (`~/Library/Application Support/Claude/claude-code/<version>/claude.app/Contents/MacOS/claude`), the same rule the model server runs it by (`src/claudeCommand.ts`, `zero-touch/scripts/readiness.mjs`); for a change job, git (said when the job is asked for, see "A new app is saved with git"); and, for Hand-off with tests or repeated changes handed off, whether the project folder is set up with git (`• This project folder isn't set up with git, so new tests and repeated changes can't be checked in a test copy here; Claude does them itself in this folder. New documents are still handed off.`, said after the check and in the start lines of a chat in such a folder; in that folder a Hand-off chat treats tests and repeated changes as its own work from the start, says so with the message that asks for them, and never refuses one file at a time). In the first chat after install a missing piece replaces "send your request again" with "once the missing piece below is fixed, ask again in a new chat". The same lines show at every chat's start while something is missing. Off needs nothing and says nothing. Tests: `tools/test/zero-touch-readiness.test.mjs`.

**Google.** The workflow models "Opus 5 + Flash 3.8" and "Fable 5.1 + Flash 3.8" and a hand-off typist "Flash 3.8" need Google. Whether this computer is connected is answered by mmo's own rule (`plugin/scripts/verify-setup.mjs`, which zero-touch carries a copy of in `zero-touch/scripts/google.mjs`; `tools/test/zero-touch-google.test.mjs` proves the two agree): an API key (`GEMINI_API_KEY`), or a Google login file that is readable and complete (the one `gcloud auth application-default login` writes, or `GOOGLE_APPLICATION_CREDENTIALS`); a project name alone is not a login; a configured file that cannot be used is "broken". For zero-touch, a Google Cloud sign-in also needs a project (without one Flash cannot run): `GOOGLE_CLOUD_PROJECT`, the sign-in file's own (`quota_project_id`, `project_id`), or gcloud's own configuration (`gcloud config set project`), read from files only; with none, the state is "no-project" and the line says `This computer is signed in to Google Cloud, but no Google Cloud project is chosen for it …`. mmo's own setup check (`/mmo:setup`) does not apply this project rule. It is checked offline at every chat's start, before zero-touch starts a workflow, and when Flash is chosen in the settings box; at that moment one real request is made too (`gcloud auth application-default print-access-token`, at most 3 seconds), so an expired login is said at once; only a sign-in Google turned down counts (expired, revoked, "please run gcloud auth"), while Google not being reached (no network, a proxy, a timeout) says nothing, and gcloud's own words never reach the person (they go to Claude's note only). Google settings found only in the shell's start-up files (`.zshrc`, `.bash_profile`, …; names only, never values) are said as "set up for the terminal only": the Claude app reads Claude's own settings file, never those. Every Google line ends with one sentence the person can say, "help me connect Google for zero-touch"; a message that names zero-touch and Google gives Claude fixed steps (`messages.mjs` `connectGoogleNote`): an AI Studio key in the `env` block of `~/.claude/settings.json` (`GEMINI_API_KEY`), or a Google Cloud sign-in plus `GOOGLE_CLOUD_PROJECT` there, then a new chat; Claude never asks for, reads, writes or repeats a key. Its line says what will happen: with no login, workflows won't start (the start refuses); with a login Google refused, workflows still start (the offline check passes, and a workflow's start-up check builds the model's connection without calling it), so the line says their Flash 3.8 steps can't run and they may stop or use another model for them. In hand-off mode the same rule is asked at every use, never kept (`lib/handoff.mjs`): while Google is not connected, a kind of work set to Flash 3.8 is done by the chat's own model. The line after the message says so, its tool is refused before it reaches the server, and a new file of that kind may be typed by hand; other kinds are handed off as usual, and connecting Google mid-chat counts from the next message. A login that stops working later is reported at the first real call, where the workflow's pre-flight or the hand-off receipt says so (a hand-off's last attempt is the chat's own model).

**Each chat is decided once, when it starts** (`plugin/scripts/ambient/lib/chat-mode.mjs`). At the chat's start moment (`SessionStart` with source `startup`, `clear` or `fork`, each a new chat id; a `fork` is a chat made by `/branch`, marked from the settings in force now like any new chat, and, when a workflow runs in another chat of the folder, told once at its first message that the workflow carries on only there: `Zero-touch: this branch can't carry on the bug-fix workflow running in another chat of this folder …`) the zero-touch plugin's start hook writes the chat's marks (`zero-touch/scripts/mark.mjs`): its record `sessions/<id>/chat_mode` and its models. Every moment of that chat acts on them, so a change of settings or plugin state reaches new chats only: a chat with no record is off (it started while the plugin was disabled, or before it was installed, or in Off), and a reopened chat (`resume`) and a compaction keep what they have. Claude Code applies a plugin enable or disable to new sessions, and to an open one only on `/reload-plugins`; a plugin loaded that way into an open chat finds no record there and does nothing.

**Why the zero-touch plugin holds none of mmo's code.** Claude Code gives each plugin its own copy of any file it links to at install, so a zero-touch plugin carrying `mmo`'s code would need a second copy of it on every machine. All of zero-touch's workflow and hand-off code stays in `mmo`; `zero-touch` depends on `mmo`, keeps the settings and marks chats. Where it needs one of mmo's rules (the chat-record paths, the Google check) it carries a copy, and a test proves the copy equal.

**The two start hooks run at once.** Claude Code runs both plugins' `SessionStart` hooks at the same moment, so `mmo`'s can run before the record exists (the chat's start is then logged `late`). `mmo`'s start work (its log line and the old-records sweep) then runs at the chat's first moment that has the record.

Without a record (and without `MMO_AMBIENT`), the shell shim in front of every mmo zero-touch hook (`plugin/hooks/ambient.sh`) exits before `node` even starts: it reads the chat id from the start of the hook input, and an id it cannot read with certainty goes on to `node`, which decides. The zero-touch plugin's own settings hooks (`zero-touch/hooks/settings.sh`) do the same for every tool call and message, and start `node` only in a chat that waits for its first settings, has a settings box open or start lines waiting, or for a message that names zero-touch (a generous text match in the shell, `zero.{0,6}touch`; node decides with the exact rule, and `tools/test/zero-touch-prompt-kind.test.mjs` proves the shell match never misses a message the rule matches). Tests: `tools/test/zero-touch-plugin.test.mjs`, `tools/test/ambient-chat-decision.test.mjs`.

## The sixteen hooks

Zero-touch's workflow and hand-off hooks are registered by the zero-touch plugin, in `zero-touch/hooks/hooks.json` (mmo's own `plugin/hooks/hooks.json` registers none of them, so a person without zero-touch has none of them). Each runs `zero-touch/hooks/mmo-hook.sh`, which finds the installed mmo's folder (the one Claude Code's record of installed plugins names, kept by zero-touch's start hook; else the mmo of the same version beside zero-touch; else this repository's layout) and runs mmo's POSIX shim `plugin/hooks/ambient.sh` there with the hook's input unchanged. All have a 5-second timeout (`turn-end` 30 seconds, because it may save a finished new app with git), all exit 0 (a decision travels as JSON on stdout, never as an exit code), all are handled by `plugin/scripts/ambient/hook.mjs`:

| Hook | Moment | Does |
|---|---|---|
| `session-start` | `SessionStart` | The chat's log line and the once-a-day sweep of old records. |
| `prompt` | `UserPromptSubmit` | Reads the message with fixed rules ($0, no model). A recognised job gets the instruction to start its workflow, with the person's models in its arguments; a typed `/mmo:` workflow command makes the chat that workflow's run; while a workflow runs, a new job asked for in plain words is queued, and a typed workflow command gets the Queue-or-Replace question; any other message gets nothing. |
| `pre-skill` | `PreToolUse` on `Skill` | Guard B: a `/mmo:` workflow starts only when routing recognised the message, the person typed it, or the queue or a replace starts it; the chat starting a second one mid-run is refused and its job queued, unless the new one could not start anyway (then it is refused with that reason). It only allows or refuses: the start is recorded once the call really ran (`post-skill`). |
| `pre-any` | `PreToolUse` on every tool | Guard A: while a recognised job waits for its workflow to start, while the question waits for its answer, and while "Queue it" holds a typed command's steps, tools that change something wait. It claims the chat's run: the run id in the orchestrator's own logging calls (`mmo-log.mjs` / `write-provenance.mjs --run-id=…`) is this chat's run, so stopping a run never guesses. In a run zero-touch started, the run-start check's command gets the person's policy file, as the model-server calls do (and, when the helpers follow the chat's model, that model in front of it), but only when there is no doubt which word is the check (`lib/run-check.mjs`): one plain `node …/driver-model-check.mjs …` call, or the shapes the orchestrator usually writes around it: a leading `cd <folder> &&`, a trailing redirect or `; echo …`, an unquoted `$(pwd)`, provided the script is named exactly once, as the word right after a `node` word that starts a command, with no here-document and no substitution before it. Any other command (the script named twice, `sed` or `grep` on it, a substitution around it) is left exactly as written. In a hand-off chat it also carries the safety net: a new document or test file typed by hand is refused, unless the person keeps that kind of work in the chat or it cannot be handed off (Google not connected). |
| `pre-dispatch` | `PreToolUse` on `load_policy`, `preflight_dispatch`, `execute_with_model`, `execute_batch`, `simulate_policy` | Inside a workflow zero-touch started: stamps the call with the person's policy as an explicit file (`policy_path`), which the server and the run-start check put ahead of everything, a project's `routing-policy.yaml` included. Helpers' calls too. A workflow the person typed is left to its own rules. (`execute_stage` takes no policy: it reuses the one pre-flight recorded.) A call whose apply-form packets would make the server run a check or format command the person's Claude settings forbid is refused (`Zero-touch: this workflow step wasn't run, because it would run a command your Claude settings don't allow.`): the server runs those commands outside Claude Code's Bash rules. Only packets the server will apply count (`apply.write` true; for `execute_batch`, only the `packet_ids` it names when it names any), each with its typed `checks` (every `run` and `fix` on the file, and every `run` on its `baseline_from` file, which the server tries first), or else its `verify` and `format` commands; they are read from the call, or from the packets file it names in the project folder. A packets file that cannot be read, or a command with shell syntax the check cannot see through (a lone `&`, `$`, backquote, brackets, redirects, a backslash, a new line), is left to Claude Code's own prompt. |
| `post-skill` | `PostToolUse` on `Skill` | Records a routed workflow's start once its command really ran, and takes the project for it atomically; when another chat took the folder a moment before, the model is told not to carry the command out and the person why. Gives Claude zero-touch's note beside the unchanged command (the tag's policy and cost recording, the brief or description, how to hand the chat back after an early stop); a command the person typed in a zero-touch chat gets only the last part. |
| `post-question` | `PostToolUse` on `AskUserQuestion` | Reads the person's answer to the Queue-or-Replace question, acts on it, and shows them what happened. |
| `pre-agent` | `PreToolUse` on `Agent` / `Task` | The five mmo agents run only inside a workflow, and not while the question waits; the chat hiring one by itself is refused. |
| `turn-end` | `Stop` | Ends a queued typed command's hold; once the chat's workflow has ended, says how (finished, stopped, failed, or stopped before it began; a finished new app zero-touch started is saved with git first, and the line says so), and continues the turn with the first queued job: its start instruction is the Stop hook's `additionalContext`, which reaches the model and lets the conversation continue, never a "block" reason, which the person would read as "Stop hook feedback" with the command and its arguments in it. A start announced at the message but never made in the turn is dropped and said. |
| `turn-failed` | `StopFailure` | A turn that ended in an error (a usage or rate limit) never reaches `turn-end`: the same clean-up runs here (the hold ends, an ended workflow lets go). Says nothing; Claude Code ignores its output. |
| `session-end` | `SessionEnd`, reason `clear` | `/clear` gives the conversation a new chat id, and Claude Code ends the old one first. A workflow abandoned that way is recorded as stopped (as "Replace it" stops one), only if the chat has claimed its run (never a run found by time, which may be another chat's), and its project is freed either way, so no later workflow there is refused. Other endings keep it: that chat can be reopened and carry on. |
| `pre-model-switch` | `PreModelSwitch` | Hand-off mode: refuses a switch away from the chat's model. Workflow mode: refuses one only while a workflow zero-touch started runs and its helpers follow the chat's model (no helper setting); otherwise answers nothing. |
| `post-model-switch` | `PostModelSwitch` | Both modes: keeps the model the chat is on now, so each line names the model really in use and the next workflow start is judged on it. Decides nothing. |
| `pre-handoff` | `PreToolUse` on the hand-off tools | In a hand-off chat: stamps the call with the chat, the project folder and who pays, after making sure the chat's models are resolved; refuses a call for work the person keeps in the chat. In a workflow-mode chat and inside a workflow run: refuses the call with the reason. |
| `post-handoff` | `PostToolUse` on the hand-off tools | Shows the person one line written from the tool's receipt. Decides nothing, adds nothing for the model. |
| `handoff-failed` | `PostToolUseFailure` on the hand-off tools | A hand-off call that failed or that the person interrupted: its new file is handed back so Claude can write it, and an interrupted call is marked by its id, which the server reads before it writes anything, so a stopped hand-off never lands later. Says nothing. |

In a hand-off chat the same `prompt` hook recognises hand-off work instead of workflow jobs, and `pre-skill` lets a workflow start only from a typed command ("Hand-off mode" below).

**The zero-touch plugin's own settings hooks** (the other five in `zero-touch/hooks/hooks.json`): `SessionStart` (the chat's marks and start lines, and where mmo is installed), `UserPromptSubmit` (start lines that waited, the first chat's note, a closed box, and this chat's facts with the box when a message names zero-touch), and around the settings box `PreToolUse` on `AskUserQuestion` and on every tool, `PostToolUse` on `AskUserQuestion` (all but the first through `hooks/settings.sh`; see "Choosing" above). They run in every chat, Off included, which is what lets the settings be changed from any chat.

**The workflow's own steps run without permission prompts**, because in Claude Code's default "ask" mode a workflow would bring dozens of prompts naming this plugin's bookkeeping scripts and model-server tools. While a workflow runs in a zero-touch chat, `pre-any` (and `pre-dispatch`, for the calls it stamps) answers "allow" for exactly two things: a shell command that is one call of one of the plugin's own step scripts (`node "<this plugin>/scripts/<name>.mjs" …`, or zero-touch's two in `scripts/ambient/`, the names in `lib/own-steps.mjs`, with no other shell syntax: no `;`, `&`, `|`, backquote, `<`, `>`, new line, and no `$` except the literal `"$(pwd)"` the workflow texts pass; for a feature run's own orchestrator only (`brownfield-orchestrator`, which wraps long calls and chains its bookkeeping), a call wrapped over lines with a backslash directly before each line feed counts as the one call the shell joins it into, and calls joined by `&&` count when each is one of those steps; `plan-lint.mjs`, `plan-to-packets.mjs` and `findings-to-packets.mjs` write only inside the run's own folder, `.sdlc/runs/<run-id>`, and refuse any other; the one setting allowed in front is `CLAUDE_CODE_SUBAGENT_MODEL=<model>` on the run-start check, which zero-touch puts there itself), and a call of the plugin's own model-server tools, except one whose packets would make the server run a command the person's Claude settings forbid, or whose packets file or command cannot be checked (that one keeps Claude Code's own prompt; in a workflow zero-touch started it is refused, as `pre-dispatch` above says). Every other command, file edit and tool keeps Claude Code's own rules and prompts; a chat without a running workflow, and a chat without zero-touch, are untouched. Tests: `tools/test/zero-touch-workflow-life.test.mjs`, and `tools/test/zero-touch-own-steps.test.mjs` (every script call in the workflow texts is a step; every server tool that takes a policy file is stamped).

The pipeline's own hooks (the write contract, the foreground-helpers guard, telemetry, the executor guard) are not zero-touch's and keep their own settings, with no short timeout: Claude Code lets a tool call through when its guard hook times out. The three that run a script with node go through `plugin/hooks/node.sh`: without Node.js it exits 0 and prints nothing (otherwise each would fail with "node: command not found" on every file write, edit and helper launch, and nothing they guard can run without node anyway); with it, `exec` passes the script's input, output and exit code through unchanged, so the write contract's refusal (exit 2) still reaches Claude Code.

## Settings and who may change them

The person's zero-touch choices are made in the settings box (above), not here. What remains is mmo's own, in layers, weakest first: shipped defaults (`plugin/config/ambient.default.json`), then `~/.mmo-ambient/ambient.json`, then `<project>/.sdlc/ambient.json`, then `MMO_AMBIENT`. None of the files switches zero-touch on or off, or chooses its models.

| Setting | Values | Default |
|---|---|---|
| `routing` | on / off | on. Off: no workflow is ever started from chat, and the chat may not start one by itself. A Workflows chat says so: its start lines in every chat, and the first message that asks for a job: `Zero-touch: the bug-fix workflow didn't start, because workflows from plain words are switched off for this project by a setting file in it, so Claude answers it normally.` |
| `routing_defaults` | `{auth}` | `estimated`: the cost recording a routed workflow starts with (it travels in the start arguments). It also says how a hand-off's Claude typist is paid for. One exception, per chat (`lib/claude-login.mjs`): in `estimated` the model server's Claude typist (a `claude -p` child) is given no `ANTHROPIC_API_KEY`, so a person whose only Claude login is an API key exported in their shell would have typists with no login at all. When `ANTHROPIC_API_KEY` is set, zero-touch asks once per chat, at no cost, whether a typist would be logged in without it (`claude auth status --json`, run with exactly the typist's environment and the server's own `claude`; kept in `sessions/<id>/claude_login.json`); only when it would not, that chat's workflows and hand-offs carry `vendor`, which hands the typist the key (the same bill as the chat itself). A key beside a plan login, a key in `~/.claude/settings.json`'s `env`, an `apiKeyHelper`, or a check that cannot answer change nothing. Test: `tools/test/zero-touch-claude-login.test.mjs` |
| `retention_days` | a whole number of days | 30 |

A project file is anyone's input: anyone who can land a commit can edit it. It may only switch `routing` off, never on, and nothing else. (Keeping zero-touch out of one project entirely is Claude Code's own job: disable the zero-touch plugin at project scope.) A value of the wrong type is ignored; an unknown `routing` value means off. A key the plugin does not know is ignored, a `handoff` block or a `routing_defaults.policy` included.

## Routing a recognised task to its workflow

With zero-touch on, an ordinary chat message that asks for one of the eight `/mmo:` jobs runs that job's workflow exactly as typing the command would. The jobs are greenfield, docs, bugfix, feature-extend, feature-new, refactor, test and deps. Every other message is an ordinary chat.

**What the person sees.** Nothing in zero-touch's own words names the plugin, a command or a model:
- **A clear request** ("fix the /login endpoint returning 500"): one plain line, "Running this as a full bug-fix workflow.", then the workflow's own steps and approvals. Three of the workflow's own setup questions are answered instead of asked: the models (the person's pick in the settings box, carried in the start tag), the cost-recording mode (`routing_defaults.auth`, in the same tag), and, for a new app, the brief (the person's message is the brief, written in the Project Brief layout). Every phase, gate and approval is the workflow's own.
- **An unclear request** (typos, casual wording, anything the rules do not recognise) that still shows work is asked for: Claude judges it (below, "Recognition"). It either starts one of the jobs the folder allows, checked by zero-touch exactly like a recognised start, or answers normally.
- **Anything else:** an ordinary chat.

Nothing has to be set in a file first: the first chat after install asks for the settings in the box.

**The chat's model.** A workflow's five helpers are mmo's own, unchanged: their agent files name no model, so Claude Code runs them on the person's `CLAUDE_CODE_SUBAGENT_MODEL` setting when there is one, and otherwise on the chat's own model. Each of zero-touch's workflow model choices plans with one Claude model (Opus 5; Fable 5.1 for Fable 5.1 + Flash 3.8; `plans` in `zero-touch/scripts/settings.mjs`, checked against the workflows' own router by `tools/test/zero-touch-chat-model.test.mjs`), so with no setting the chat must be on that model:
- the start message says so, with why: `• Workflows need this chat on Opus 5, because you chose Opus 5 + Flash 3.8, where Opus 5 plans and reviews, and that part runs on this chat's own model. …`; in the first chat, a save made while the chat is on another model says it at once and does not judge the first message, and in every chat, not only the first, while the chat is known to be on another model or the person's setting names another one;
- a recognised job is checked against the chat's model before it starts (`startProblem` in `lib/route-flow.mjs`), again when the workflow's command is called (`pre-skill`), and once more at the workflow's first step that changes or spends anything (`wrongModelAfterStart`). Claude Code passes no model to these hooks, and a new chat's first message comes before the chat has answered; at the command's call the app may not have saved Claude's reply yet, but by the first step it has, so its transcript names the model. On another model the workflow is stopped there, before any of its work, and the rest of the turn is held with the usual line;
- the run's own model check, mmo's own and unchanged, is told the chat's model (`CLAUDE_CODE_SUBAGENT_MODEL=<model>` in front of the orchestrator's call of it, `lib/run-check.mjs`): a fact it then judges itself, as it judges a typed run's setting;
- while a workflow zero-touch started runs, switching the chat to another model is refused (`pre-model-switch`: `Zero-touch: this chat stays on Opus 5 until the bug-fix workflow ends, because the workflow's helpers use this chat's model. You can switch once it has finished.`), unless the person's own setting decides the helpers' model. A switch that passes is recorded (`post-model-switch`), so the next start is judged on the model the chat is really on.

**What the app shows is not zero-touch's to change.** Once a workflow starts, the app lists the command start ("Ran skill /mmo:greenfield") and the workflow's helper agents in its activity rows, and the workflow's own messages keep its own wording: exactly what a typed run shows. A plugin cannot rename those rows, for two reasons:
- Claude Code starts a plugin command only by its full `plugin:command` name. A bare `greenfield` is refused with "Did you mean mmo:greenfield?".
- Command aliases exist only for Claude Code's built-in skills. A plugin's command file cannot declare one.

Only renaming the plugin would change those rows, and a rename changes every typed `/mmo:` command too.

### The outcome contract

A hook cannot start a workflow: on the person's message Claude Code lets it add a note, set the chat's title, or block the message, so every start is Claude calling the workflow's command, and Claude may instead question the size of a job, ask which the person wants, or do the work itself. So every message in a Workflows chat ends in exactly one of: **A** the workflow starts, with the person's models; **B** Claude answers normally; **C** one line says why nothing started and what to do. The hooks enforce it:
- every start Claude is told to make says the person chose a full workflow for every job, small ones included, and not to question its size or cost or offer to do it in the chat (`CHOSEN_FULL`);
- until a recognised job's workflow starts, nothing that changes a file runs (Guard A);
- a job that cannot start (another chat's workflow in the folder, the chat's model, Google, git) is outcome C for its whole turn: the person reads why and what to do, and nothing that changes a file runs and no workflow call goes through until the turn ends (`route.json` status `refused`), so Claude cannot do the job by hand instead, whatever it makes of the note. The first chat's first message, when the chat must switch model first, is held the same way (`zt_replay.json` with `waits`) and never judged at the turn's end: the person sends it again after switching;
- a turn that ends without the start is continued once with "start it now" (`retryInstruction`; `route.retried` and Claude Code's `stop_hook_active` both stop a second push, so it cannot loop);
- still not started: the line `Zero-touch: the bug-fix workflow didn't start. Say "yes" to start it now, or ask for something else.`, and the job is kept for one message (`zt_carry`): a plain yes ("yes", "go ahead", "full build", "run the full build anyway"; never with a negation or a question) starts it through every start check and the folder rule; anything else drops it;
- a start Claude makes on its own judgement is checked as any start (the job is one the folder allows, the chat's model, Google, one workflow per folder), and zero-touch writes the run's tag itself.
`tools/test/zero-touch-outcomes.test.mjs` is the table: what zero-touch decided about a message × what Claude then does, each cell ending in A, B or C, run through the real hook with no model call.

### Recognition (`lib/route.mjs`)

Fixed patterns first, then Claude's judgement for what they cannot place. Two signals must agree.

**Claude's judgement.** A message the rules could not place ("no job verb opens it", or "names nothing in the software"), of three words or more, that is not a reply ("yes", "ok go ahead") and shows work is asked for (a job verb or a fault anywhere in it), is given to the chat's Claude with the jobs this folder allows, each in one line, and when to start one: only when the message itself asks for that job now; never for a question, a request to explain, review, run, deploy or commit, a reply, a tiny edit, or when unsure. The chat's own model judges; no other model is called. A start it makes is checked by zero-touch (the "judge" route in `pre-skill`), so a judgement can never start a job the folder does not allow, on the wrong model, or beside another workflow; and a start only passes on the chat model the person's models plan with (Opus 5, or Fable 5.1). Measured offline on a generated set of 208 labelled realistic messages: of 128 that should start a workflow, 37 start by the rules and 74 more reach Claude's judgement; of 80 that must not, 45 are stopped by the rules, 32 reach Claude (which must answer them normally), and 3 start wrongly by the rules, all "two jobs in one message" cases. How well Claude judges is not measured (it needs model calls).

**The message** must be an instruction whose job verb opens it.
- **A project job** must also name something in the software: a path or file, a code identifier, an HTTP status, an error type, or a word of the trade (bug, test, endpoint, module, …). This is a positive requirement, never a list of exceptions.
- **A new app:** the app word must head what is built. "A haiku about a bot" is a poem: no preposition may sit between the article and the app word.
- **A pasted brief** counts only in `/mmo:greenfield`'s own layout (`# Project Brief`), and not when it ends with a question.
- **Clauses:** a message is cut at "and", "then" or ";" only where a new instruction follows (a verb such as run, add, fix, or one of the eight jobs). Any other part after "and" is still part of what the first clause names: "write unit tests for the discount and tax functions in src/cart.js" is one test job about `src/cart.js`. The "it / this", small-edit and negation checks still read only what comes before the "and", so "fix it and the tests" stays a follow-up. A word that can be a verb or a noun counts as a verb, so an unsure part is cut, and the worst case stays a missed route.
- **Two jobs** route anyway, because each is part of its own job: a bugfix plus its regression test, and an upgrade plus fixing what the upgrade broke.
- **Never routed:**
  - questions (a `?` without "can you");
  - negations, including a self-negating object ("fix nothing yet");
  - "fix" as a noun;
  - follow-ups (also / as well / too / again);
  - a bare "fix it";
  - text in the message: "the code below", "the error above", "described below", "the following", "the attached log". "below" and "above" count as pointers only when they close the noun they follow; followed by an amount or a determiner they are a comparison and part of the bug ("…can go below zero", "quantities above 99", "prices above the limit"). What may follow a comparison is a closed class of English words (numbers and determiners), so this is a grammar rule, not a list of cases;
  - small edits: typo, spelling, grammar, formatting, lint or a commit message as the thing named (the head of the object). "The bug where comments are not saved" and a brief listing "ticket comments" are not small edits;
  - two different jobs.

**The folder** (`lib/route.mjs` `folderKind`, `lib/repo-kind.mjs`):
- **Existing:** `/mmo:greenfield`'s own four signals of an existing repo, or any source file of its own (dependencies, build output and docs do not count; a file counts whatever the case of its extension).
- **New:** everything else.
- A new folder can only be greenfield; an existing project only a brownfield job.
- Nouns that can be a whole app (api, service, dashboard) are unsure in an existing project.

### Starting the workflow (`hook.mjs`, `lib/route-flow.mjs`)

Every workflow start, typed or model-started, reaches the hooks as a `PreToolUse` on the `Skill` tool. A typed `/mmo:bugfix`, or `/bugfix` where Claude Code allows the plugin's command without its prefix, makes the chat a workflow run before any tool runs. Only the ten workflow commands do (`greenfield`, `brownfield` and its seven per-job commands, `pass`): a typed one-off command (`/mmo:setup`, `/mmo:policy`, `/mmo:revert`) writes no run log, so nothing could ever end its run, and it leaves the chat as it was.

1. **Like typing the command, whenever the chat is idle.** A job message starts its workflow at any point in a chat, as often as the person asks, one workflow at a time. Nothing is routed:
   - **while a workflow is running in the chat** (then a new job is queued, below). Running means from the moment the chat starts it (typed or routed) until the workflow's own log (`<project>/.sdlc/runs/<run-id>/orchestrator.log`, written through `mmo-log.mjs`) shows it ended: every gate it opened answered after its `run.end`, an answer of `abort` at any gate, or a `run.end` that says aborted or failed. The run is the one the chat claimed (the run id in its orchestrator's own logging calls, seen by `pre-any`); until then, the latest one whose `run.start` is not earlier than the chat's start of the workflow (`lib/workflow-log.mjs`). A run in the same folder that another chat started later (a chat without zero-touch takes no project lock) is therefore never taken for this chat's once it has claimed its own. A workflow with no logged run yet (stopped at its first questions, or still asking them) keeps the chat, so an answer to one of its questions is never taken for a new job. Once it has ended, the next message is judged afresh: a job starts its own workflow (or the first queued one starts by itself), anything else is an ordinary message;
   - **for a message typed while Claude is still working, when no workflow runs.** Claude Code records such a message in the transcript as a `queued_command` and delivers it into the running task; an ordinary message is a plain user entry. Every message also passes Claude Code's input queue, recorded as `queue-operation` entries: an idle one is enqueued and dequeued at once, one typed while Claude works waits there, and in the terminal the prompt hook runs at Enter while the text is only enqueued. The prompt hook replays the queue first (a text still waiting was typed mid-turn), then reads the newest transcript entry carrying the message (`lib/transcript.mjs`, `sentWhileWorking`; zero-touch's copy in `zero-touch/scripts/prompt-kind.mjs`, kept equal by `tools/test/zero-touch-prompt-kind.test.mjs`); a queued one joins the running task, never starts a workflow and never ends a start that task has pending (logged as `route.none` with the reason "sent while Claude was working");
   - **for a notice nobody typed** (a background command's completion notice, which Claude Code delivers through the same hook, tagged): logged as a prompt nobody typed, never judged.
   Work the chat has already done does not hold a job back, exactly as it would not stop the person from typing the command.
2. **A clear route.** The prompt hook tells the chat which workflow to start (the Skill call, and its arguments: the tag `[zero-touch policy=<name> auth=<vendor|estimated>]` with the person's models and the cost recording, then the person's own words for the job), and the plain line to say. mmo's command texts say nothing about the tag: when the command loads, the `post-skill` hook gives Claude zero-touch's note beside it (`runNote` in `lib/route-flow.mjs`): the tag's policy is this run's, as an explicit file that wins over the project's saved choice and over a repo-local `routing-policy.yaml`, as `/mmo:pass --policy` does; the cost recording is not asked; the helpers follow the chat's model, which zero-touch checked, so the person is not asked to set anything; and how to hand the chat back if the workflow stops before its run begins. A command the person typed gets only that last part. It is a tag and not flags on purpose: a person typing a command gets exactly the surface they had. A route belongs to its prompt, and the next prompt drops it.
3. **Guard A** (one catch-all `PreToolUse` hook, `pre-any`). Until that Skill call, only tools that change nothing run (Read, Glob, Grep, ToolSearch, TodoWrite, the web tools, Skill). Everything else waits with "Start the workflow first", including every other MCP server's tools and helpers already running.
4. **Guard B** (`pre-skill`), for a `mmo:` Skill call (a leading `/` is the same command):
   - **Allowed:** a command the person typed (its own Skill call, in modes where a typed command makes one), the routed workflow, and a queued or replacing one the hook itself started; while a workflow runs, any of the plugin's non-workflow skills (its manual) and one-off commands.
   - **Refused:** a helper agent starting the chat's workflow, a one-off command (setup, policy, revert) or workflow the chat starts by itself outside a workflow run, a second workflow beside the routed one, and one the folder rule forbids.
   - **Queued:** the chat starting a second workflow by itself while one runs is refused and its job queued, as the person's own words are, unless the new one could not start anyway (its models need Google and there is none, the pre-built server is missing, its start-up check fails): then it is refused with that reason.
   - Guard B only allows or refuses. It records nothing: a call it allows can still be stopped by Claude Code's own permission rules, another hook or an interrupt.
   - **A start the chat makes by itself** (no route from the rules): always refused. The person reads `Zero-touch: a full workflow starts only for a request zero-touch recognises, so Claude carries on in the chat.`; the model is told not to start one and not to mention commands. A message that looks like a job but is not routed also gives the model that instruction up front, so it does not try.
   - **Every refusal is written for the person:** Claude Code shows a refusal's reason to the person (in red in the desktop app) as well as to the model, so the reason is one plain sentence, and the model's exact instruction travels separately as the refusal's `additionalContext`. `tools/test/zero-touch-person-text.test.mjs` builds every person-visible string and fails on tool, command, plugin, policy, file or variable names, JSON, `/clear` or a doubled full stop.
5. **Starting.**
   - The start is recorded by the after-hook (`post-skill`), once the command really ran (recording it before the call would mark the chat as running a workflow even when the call is then refused). The chat is marked a workflow run with the person's policy on its record, and the project is taken for it atomically: when another chat took the folder a moment before, the model is told not to carry the loaded command out and the person why. Nothing is written into the project: the models travel in the start arguments, and `pre-dispatch` stamps them on every model-server call of the run.
   - A start announced at the message ("Claude is starting the …") that Claude never makes in that turn is dropped at the turn's end and said (`didn't start after all`).
6. **When a workflow cannot start,** nothing starts and the chat tells the person the real cause, with the fix for that cause:

   | Cause | Fix offered |
   |---|---|
   | The person's models use Flash and this computer has no Google login (mmo's own rule, "Google" above) | Connect Google (Claude can walk them through `gcloud auth application-default login`), or choose models without Flash in the settings box |
   | The plugin's pre-built server is missing (only a damaged copy: the plugin ships it built; called "not set up") | `verify-setup.mjs --fix` |
   | The chat is on another model than the policy plans with (no helper setting), or the person's helper setting names another one | Switch the chat with the model menu (the line names the model and the terminal command); or ask Claude to help change the setting, or choose other models |
   | Anything else the workflow's own model check refuses (a policy that does not plan with one Claude model) | The check's own reason, passed on to Claude; the person reads a plain line |
   | Another chat in this project is running a workflow (the project lock) | Ask again when that one has finished (a workflow that never began frees the folder by itself after 30 idle minutes) |

   The check is asked with the person's policy as an explicit file (`--policy-path`), so a project's own `routing-policy.yaml` decides nothing here either. Under `vendor` the helpers'-model check is skipped, as the workflow itself skips it. A project's saved choice, or a saved file that does not read, does not block a start: zero-touch does not read it.
7. **Ending.** A workflow's end is read from facts, never from the model remembering to say so:
   - its own log shows it ended (`lib/workflow-log.mjs`): an abort at any gate, a run end that says aborted or failed, or a completed run whose final acceptance (Gate 4) is answered. mmo logs its run end right before its final report and opens Gate 4 after that report, often from a helper working in the background while the chat's own turns end, so between the two the run is still running and a queued job waits. A completed run that never logs Gate 4 is over once nothing in it is open and its log has been quiet for ten minutes. The chat reads only its own run: a run that started before its current workflow did (an earlier workflow still logging its last steps) is never taken for it (`hook.mjs` claimRun); a gate answered "revise" (Gate 4's "reject: …") keeps the run going until the revision is approved;
   - the person types "stop", "cancel", "abort", "never mind" or "forget it" (the whole message; "stop the dev server" is not this) in a workflow zero-touch started, while it works or before its run begins (at a gate, and in a workflow the person typed, the word is the workflow's own answer, so mmo's own abort records the end): the run is stopped the way its own abort stops it, its queue is dropped, and the folder is free. Typed while the workflow is working, the stop is recorded (stopping at once would switch its file rules off and free the folder while its helper keeps writing), the person reads `Zero-touch: stopping the bug-fix workflow, as you asked, as soon as Claude's current step ends. …`, Claude is told to start no more steps, and the stop is carried out when the turn ends (`turn-end`, `turn-failed`), or at the next message when the turn ended without the Stop hook (Esc). "Replace it" written out mid-turn neither settles nor drops the question; the box stays;
   - the workflow stopped before its run began (the person said no to the plan, a check failed, the folder was wrong): Claude runs zero-touch's `plugin/scripts/ambient/workflow-stopped.mjs` at each such stop (told so by the note beside the command, above; mmo's command texts are unchanged), `pre-any` sees the call, and the chat and the folder are handed back when the turn ends;
   - the conversation was rewound (`/rewind`, or an earlier message edited in the desktop app) to before the workflow started: Claude Code keeps the old entries in the transcript but continues from an earlier one, so at the next message the hook walks the conversation back from that message (each entry's `parentUuid`, at a compaction `logicalParentUuid`, never timestamps; `lib/transcript.mjs` `onActiveChain`); when it passes the workflow's start time without meeting the start's Skill call, the workflow is stopped as its own abort stops it, the folder is freed, and the person reads `Zero-touch: the conversation went back to before the bug-fix workflow started, so it was stopped. …`. Anything unknown (no call id: a start the person typed; the chain leaving what was read; a compaction) is not a rewind;
   - a turn that ends in an error (`StopFailure`: a usage or rate limit) gets the same clean-up as `turn-end` (`turn-failed`).
8. **Around it:** `/clear` starts a fresh conversation under a new chat id: an earlier workflow run, route, question and queue no longer count, and a workflow `/clear` abandons is recorded as stopped (its claimed run only) and frees its project (`session-end`). A start zero-touch still has pending ends at the person's next message, typed command or plain words: a typed command never takes over such a start, so a run the person types never carries zero-touch's models. Three failures of zero-touch's hooks in one chat switch it off for the rest of that chat.

Tests: `tools/test/ambient-route.test.mjs` (recognition) and `tools/test/ambient-routing-hooks.test.mjs` (the start, end to end through the shell shim); `tools/test/zero-touch-workflow-life.test.mjs` (a refused start leaves nothing, the atomic folder lock, an early stop, "stop", an idle never-started workflow, a deleted chat's lock, Gate 4 revise, the resume record, a project's own `/test`, a job typed mid-turn, a turn ending in an error, the end line by outcome); `tools/test/zero-touch-lines.test.mjs` (the line after each message); `tools/test/zero-touch-routing-stamp.test.mjs` (the stamped policy, `/clear` freeing a project, the Queue-or-Replace lines); `tools/test/zero-touch-workflow-tag.test.mjs` (the tag, the note beside the command, and mmo's texts free of zero-touch); `tools/test/zero-touch-chat-model.test.mjs` (the chat's model: the planning model, the start lines); `tools/test/zero-touch-plugin.test.mjs` (the start message, the settings deciding the chat, nothing again after a compaction, Node.js missing); `tools/test/zero-touch-start-lines.test.mjs` (where the start lines go on each screen, the summary once per save, only what needs action after it, Off silent, the facts and the box when a message names zero-touch, an old Node.js).

### A second job while a workflow runs (`lib/queue.mjs`)

Zero-touch chats only; a chat without zero-touch keeps mmo's own behaviour. Why: without it, a workflow command typed while another runs (`/mmo:docs` during `/mmo:bugfix`) starts and drops the running one without a word.

**Plain words: queued at once, no question.** While this chat runs a workflow, a job asked for in plain words that the rules recognise is queued straight away, and said: `Zero-touch: noted. The documentation workflow will start by itself when the bug-fix workflow finishes, and it will wait for your approval at its first main step.` Claude is told to carry on with the running workflow. Nothing is held and no box opens. A request the rules cannot place but that may ask for work is left to Claude's judgement, as when no workflow runs: about the running work ("the parser should also handle leap years"), it stays part of it; a clearly separate job, Claude calls that job's workflow. The same goes for the chat starting a second workflow by itself: Guard B refuses the call and queues the job, said with the same line, and only a job the folder allows (never a new app in a project). While the workflow waits at one of its steps, the message is its answer: at a gate or at its first questions the message goes to the workflow ("add a due date to the form" at an approval step is a revision of the running work). "At its first questions" only when the workflow can have asked one: Claude's turn ended (a workflow's turn ends only to wait for the person) or was cut off at a question box. A message that cut Claude off in the middle of another step (the desktop app's Send on a message waiting while Claude works, Esc, an error) is queued and said like one sent mid-turn, and Claude is told to run the cut-off step again. Zero-touch knows from its own record, not from the transcript: `pre-any` keeps the name of each tool the chat starts while its workflow runs (`zt_step`), the end of a turn (`turn-end`, `turn-failed`) drops it, and one still kept at the next message means the turn was cut off. A queued job starts by itself only when the running workflow **finished** (below); a workflow that was aborted at an approval step, failed, or stopped before its run began drops the queue instead, and the end line says so: `Zero-touch: the bug-fix workflow was stopped. … The documentation workflow you queued was not started; ask for it again when you want it.` A drop at a moment that shows no line (a cut-off turn, a failed turn) is said at the person's next message, once (`zt_queue_dropped`). If Claude does not start a queued job, the outcome contract's line and "yes" apply; a command the person typed and queued is pushed again exactly as typed, never with zero-touch's tag. To replace the running workflow, the person answers its next approval step with "abort", then asks again.

**When it asks.** The Queue-or-Replace question is only for **a typed `/mmo:` workflow command** while one runs (a typed command is never a gate's answer). Its text stays with the model, which is told to ask first.

The model is told the exact question and the two labels and must ask with Claude Code's multiple-choice tool (`AskUserQuestion`); if the running workflow is waiting for its own answer, both questions may go in the same call. Until the person answers, nothing that changes anything runs (Guard A), the workflow's helpers included. The answer reaches the hook as `tool_response.answers[<question>] = <label>`, so the hook acts on the exact label, never on a guess (`post-question`). A person who types the answer instead is understood only when the message is one of the two labels; any other message drops the question, so nothing stays blocked.

**Queue it.** The job joins the chat's queue, first in first out; the same job (same command, same description) is not added twice. A command the person typed is queued as typed (also when the same job was already queued from their words: their typing wins) and starts exactly as typed, with its own questions and rules: no zero-touch models, no zero-touch start checks, nothing stamped; only a job zero-touch recognised starts with the person's zero-touch models. After a typed command, whose text the model still holds, nothing that changes anything runs until that turn ends (the hold). At the end of the turn in which the running workflow's own log shows it finished, the turn continues with the first queued job (the `Stop` hook's `additionalContext` tells the model to start it with the Skill tool, one plain line first); Guard A holds everything else until it starts. A start the model does not make is not pushed again in the same turn (`stop_hook_active`): the job stays queued for the next turn's end. The queue ends with the chat or `/clear`.

**Replace it.** The running workflow is stopped the way its own abort stops it (`lib/workflow-log.mjs` `abortRun`): the chat's claimed run, or, when the chat has no claim (a run id the model left as a shell variable), the run found by time, unless another chat has claimed that one: its run log records `run.end outcome=aborted reason=replaced`, in the format `mmo-log.mjs` writes, and a brownfield write lock (`.sdlc/local/write-contract.json`) that belongs to that run is switched off, as the brownfield manual's abort step does; the run folder is kept. Then the new workflow starts: a typed command carries on as the chat's workflow; any other is routed like a recognised job.

**One workflow at a time in one project** (`lib/project-lock.mjs`). Two chats running workflows in one folder would write into the same `.sdlc/runs/` and read each other's run. A zero-touch chat that starts a workflow takes the project's lock (`projects/<key>/workflow.lock/owner.json` under `MMO_HOME`), atomically: the lock is a folder, and creating one succeeds for exactly one chat. A second chat's recognised job gets the cause "busy" (below), and its typed workflow command is kept from the model (the prompt hook blocks it; the person sees why). Whether a lock holds is decided from facts each time (`ownerStillRunning`): the owning chat must still have its workflow record, not marked stopped; its chat must still exist (its transcript, recorded at the start); its workflow's own log must not show it ended; and a workflow that never reached its run must not have sat idle more than 30 minutes (the one stated age bound: a run that has begun may wait at a gate for as long as it likes). A lock that fails a test is replaced, and the chat that lost it is told once at its next message (for a chat that was closed while its workflow ran: `Zero-touch: the bug-fix workflow in this chat stopped, because this chat was closed while it ran and another chat in this folder has started a workflow since. …`). A `workflow.json` lock file is also honoured while its owner runs. The busy cause is in the table of step 6.

**Facts it rests on** (read through the desktop app's own transport, stream-json): a `/command` sent while Claude works waits and runs as its own turn after the running one; plain words sent while Claude works join the running turn at its next step; a `UserPromptSubmit` block keeps a typed command from the model and shows the person the reason; the prompt hook of a typed command sees the typed line, with the same `prompt_id` as its expansion. A command typed with "Send now" interrupts the running turn on purpose: the question is then asked at once, and "Queue it" leaves the interrupted workflow to be resumed by the person.

Tests: `tools/test/zero-touch-queue.test.mjs`.

## Hand-off mode

Workflow mode runs a whole gated workflow for a job. Hand-off mode is for ordinary development in the chat: **the chat's own model does the work** (reading, deciding, new code, bug fixes, refactors, reviews), and only work that is mostly typing AND has a check code can run on the result goes to the model the person chose for it. Choose Hand-off in the settings box ("Choosing" above) and start a new chat.

| Kind | What it covers | The box's question | Typed by |
|---|---|---|---|
| docs | a new document of the project: a README, a guide, an API reference, a changelog | Documents | the chosen typist's policy, its `docs` stage |
| spec | a new spec: requirements, a design document, an API spec, a data-model write-up | Documents | the same |
| plan | planning text: a plan, a task breakdown or tickets, a status report, release notes | Documents | the same |
| tests | new tests for code that exists | Tests | the chosen typist's policy, its `tests` stage |
| repeat | the same change repeated across files (the chat's model makes it once) | Repeats | the chosen typist's policy, its `codegen` stage |

For each of the three questions the person picks **Flash 3.8** (the shipped policy `opus-plus-flash-v38`), **Sonnet 5** (`opus-plus-sonnet`), or **Keep in chat**: that kind is not handed off at all, and the chat's model does it with its own tools.

New code, a bug fix and a refactor are never handed off: a wrong answer there is hard to spot. **Plain words start no workflow in a hand-off chat**; a workflow starts only when the person types its command, and then runs as in any chat.

### The chat's start (`zero-touch/scripts/start-chat.mjs`, `mark.mjs`)

The start hook reads the person's settings **once** and stamps them on the chat (`sessions/<id>/handoff.json`): the chat model, and who types each kind of work, each with the shipped policy that routes it. Everything later reads the stamp, never the settings: a setting changed in the middle of a chat would leave its start message, its model guard and its hand-offs disagreeing, and would split one chat's costs across two sets of models. A change reaches the next new chat (or `/clear`, a new chat id).

| The box's question | Controls | Standard |
|---|---|---|
| Chat model | the model a hand-off chat is kept on: it does the development, decides what to hand off, and makes the last attempt when the typist fails twice | Opus 5 (`claude-opus-5`) |
| Documents / Tests / Repeats | who types that kind of work: Flash 3.8, Sonnet 5, or Keep in chat | Flash 3.8 |

**An organisation's pinned model** (managed settings `model`) outranks the person's chat model; written as an alias it cannot be compared with a model id, so the plugin then pins nothing and the organisation's setting is what holds the chat (and the typist's own policy then gives the last attempt). **A project's own `routing-policy.yaml` is not used by zero-touch** (the start lines say so in every chat in a folder that has one).

The person sees the summary once per save (see "The start lines" above): Hand-off mode is on; who does what, kind by kind; that a failed hand-off is retried by the chat's model and then done in the chat; that anything a hand-off adds can be undone; which model the chat is kept on and whether it is on it; that plain words start no full workflow; how to change it. Later chats show the chat-model line only when the chat is known to be on another model. The chat's model gets the hand-off rules (the hook's `additionalContext`) at every start, built from the settings: work kept in the chat is listed as its own, and that kind's tool is not named. A compaction drops the rules from what the model reads, so the rules are given again after a compaction and when a chat is reopened, from the stamp; nothing is shown to the person again then. A stamp with one policy for every kind reads as that policy for every kind.

### Recognition (`lib/handoff-route.mjs`)

Fixed patterns, no model. The message is read the way workflow mode reads it (the first line, polite openers removed, questions and requests to explain set aside), sentence by sentence and clause by clause. A clause is hand-off work when a creating verb opens it (write, create, draft, generate, prepare, add, …) and the thing it names **is** one of the documents above, not something that mentions one: the document word must close its noun phrase.

| Message | Recognised as | Why |
|---|---|---|
| `write a README for this project` | docs | |
| `draft a design doc for the cache layer` | spec | |
| `write a test plan for the checkout flow` | plan | the most specific word wins: a test plan is a plan |
| `add tests and docs for the parser` | tests and docs | one verb, two things, each judged on its own |
| `fix the login bug and write tests for it` | tests, beside the chat's own work | |
| `rename getUser to fetchUser everywhere` | repeat | a mechanical change verb plus where it is repeated |
| `do the same in the other three services` | repeat | |
| `add a changelog entry for this fix` | none | the thing named is an entry: an edit to a file that exists |
| `update the README with the new setup steps` | none | an update, not a new document |
| `add docstrings to the scheduler package` | none | documentation inside code files is an edit to code |
| `document the auth module` | none | unsure: a document of its own, or comments in the code |
| `fix the failing tests across the repo` | none | each failure is its own fix |

Precision first: recognition decides only the line the person sees and the reminder the chat's model gets. The model can still hand off work the patterns missed. Unlike workflow mode, a follow-up is fine here ("also add tests", "write tests for it"): nothing is started. The labelled set is `tools/test/zero-touch-handoff-words.test.mjs`.

### What the person sees after each message (`lib/handoff.mjs`)

| What happened | Line |
|---|---|
| A new document, spec or plan | `Zero-touch: Opus 5 will collect the facts and give Flash 3.8 instructions to write the new document. It's checked automatically before it's added to your project.` |
| New tests | `Zero-touch: Opus 5 will decide what to test, and Flash 3.8 will write the tests. They're run in a test copy of your project first, and only added if the result is the expected one.` |
| A repeated change | `Zero-touch: Opus 5 will make the change in one file, and Flash 3.8 will repeat it in the others. If your project has an automatic check (such as its tests), it's run on a test copy first, and nothing is changed unless it passes.` |
| A kind the person keeps in the chat | `Zero-touch: new tests are set to stay in this chat (your setting), so Opus 5 writes them directly.` |
| Work set to Flash 3.8, and this computer is not connected to Google | `Zero-touch: this can't be handed off right now, because this computer isn't connected to Google. So Opus 5 does it directly.` When other work in the same message is handed off: `the new document can't be handed off right now, because this computer isn't connected to Google, so Opus 5 writes it directly.` beside the usual sentence for the rest. (How to connect Google is in the start lines, in every chat while it is not connected.) |
| Hand-off work beside other work | the line above, then `Opus 5 does the rest directly.` |
| Anything else | Nothing (quiet by default). |
| Hand-off work that cannot run | `Zero-touch: this can't be handed off right now, because <why>. So Opus 5 does it directly.` Said once per chat and cause; the model is told every time. |
| Tests or a repeated change in a project not set up with git (after the call) | `Zero-touch: this can't be handed off here, because the test copy it needs only works in a project set up with git. So Opus 5 does it directly. (New documents can still be handed off.)` (the last sentence only when documents hand off; the server's receipt carries `cause: "no-git"`) |
| While a typed workflow runs | Nothing for an answer or an ordinary message, as in workflow mode |

The names are never guessed. **The hand-off model** is the one the chosen typist's policy gives that kind of work, asked of the workflows' own router once per chat (`plugin/scripts/handoff-models.mjs`, the same routing code the server uses) and kept for the chat. **The chat's model** is the one the chat is on now: what Claude Code last reported (the start moment, a model switch) or, when newer, the model the chat's transcript shows it last answered with; when nothing says, the line says "the chat's model". The chat's model also gets a reminder naming the tool for each recognised kind it should hand off, and, for a kind kept in the chat, that it does it itself.

### The safety net: a new document or test file is not typed by hand (`lib/handoff-net.mjs`)

Being told to hand work off is not enough. A model that types the file itself has done the expensive typing, and nothing checked the result. So in a hand-off chat the hook refuses such a write: the person reads the approved line as the refusal itself ("Opus 5 started writing the new document … itself. In Hand-off mode that work goes to Flash 3.8, so zero-touch stopped it…"), every time (so the person never believes the hand-off model wrote what Claude wrote), with the way out at its end: `To have it written here instead, say "write it yourself".` The model is told, separately, the tool that takes it with its form's fields, so the next call is the right one; and if that tool is not in its list (a chat reopened after the settings changed), to tell the person rather than write the file. It rides on the catch-all `pre-any` hook, so no extra hook runs in any chat.

What is refused is narrow on purpose:

| | Refused | Left alone |
|---|---|---|
| Which file | one that does not exist yet | any file that exists: a change to it is the chat model's own edit |
| Where | inside the project | outside it; any folder whose name starts with a dot (a tool's own); an agent's instruction file (`CLAUDE.md`, `AGENTS.md`, …) |
| What kind | a document by its file type (`.md`, `.mdx`, `.rst`, `.adoc`); a test file by its name (`cart.test.js`, `test_cart.py`, `cart_test.go`, `CartTest.java`, a code file under `__tests__/`) | code, configuration, fixtures and helpers beside the tests; anything in a test-data folder (`fixtures`, `__fixtures__`, `testdata`, `test-data`, `test_data`, `__mocks__`, `__snapshots__`: the tools cannot write such a file exactly); a spec kept as YAML or JSON, which cannot be told from configuration |
| How it is written | the Write tool; an edit that creates a file (`Edit` or `MultiEdit` of a file that does not exist, `NotebookEdit`); a shell redirect (`>`, `>>`, `>|`, `&>`) or `tee`, with every `cd` before it followed | a here-document's text and anything inside quotes (never read as a redirect); a path the command computes (a variable, a substitution); a file a program writes (a script, `cp`, `mv`) |
| Which message | a kind of work the person's message in this turn asked to hand off (a document for a document, tests for a test file) | a file of a kind the message did not ask for (a note while fixing a bug), and every file when the message asked for the work in the chat ("write it yourself", "don't hand it off") |
| How often | every time, until the file is handed off (the outcome contract) | the ways out, all deterministic: the hand-off itself; a hand-off that handed the file back; no Google or git for that kind; a kind kept in the chat; the person's "write it yourself" (or "don't hand it off") for that message |

The shell is covered because a model in an auto-approving permission mode usually writes through it. The last row's right-hand side is the net's known limit: those writes are not seen.

It stands down when handing off is not possible or not wanted: a kind the person keeps in the chat, a file a failed hand-off handed back (`handoff_released.json`: every attempt failed, its form was refused twice or for something the form cannot fix, or the call failed or was interrupted), a hand-off that cannot run here (the policy cannot be read, the server is not built), a kind set to Flash 3.8 while this computer is not connected to Google, a chat that is running a workflow (which has its own rules for what is written), another chat's workflow holding the project (then no hand-off lands at all, and Claude's own writes fall under that workflow's write contract), and any chat in workflow mode. A helper the chat started is held to the same rule as the chat.

**The chat's own edit, kept for a repeated change.** On the same `pre-any` hook, before the chat's first edit of a project file in a hand-off chat, the file's text is kept once (`sessions/<id>/handoff_before/`, up to 2 MB a file). A repeated change takes its pattern from the smaller of two differences, the chat's own edit against that text and the change since the last commit, so changes the person had not committed, and an older committed edit, are never copied into other files; with no kept text (the file was changed through the shell), it is the change since the last commit. The kept text of the example is dropped once a repeated change lands.

The person sees `Zero-touch: Opus 5 started writing the new document docs/setup.md itself. In Hand-off mode that work goes to Flash 3.8, so zero-touch stopped it and told Opus 5 to hand it off. To have it written here instead, say "write it yourself".` (or `the new test file`). A change repeated across many files is not checked this way: zero-touch cannot tell Claude repeating a change itself from ordinary edits, so whether it is handed off is Claude's choice.

### The chat stays on its model

Hand-off mode keeps the chat on the chat model the person chose, because the chat's own model does the development and decides the hand-offs: which model that is decides the quality and the cost of everything that is not handed off. (Workflow mode keeps the chat on its model only while a workflow zero-touch started runs, because the workflow's helpers follow the chat's model; see "The chat's model" above.) A plugin cannot set a chat's model, so:

- the chat's real model is read wherever it can be seen, never assumed from the setting: a reported switch, or the chat's own answers (`lib/handoff.mjs` `chatModelNow`). While it is another model than the person chose, **nothing is handed off**: a message that asks for hand-off work gets `Zero-touch: this chat is on Sonnet 5, but you chose Opus 5 to do the development in Hand-off mode, so nothing is handed off until you switch this chat to Opus 5 with the model menu next to the message box (in the terminal, type /model claude-opus-5). Then ask again.`, the hand-off tool is refused with the same line (checked again at the call: a new chat's first message comes before its model is known), and the safety net still refuses typing that work by hand. Any other message gets a warning once per model (`sessions/<id>/handoff_model_warned`), and Claude is told its real model, so it never names the setting as itself. The start summary says "the model you chose for this chat", never "this chat's model";
- the start lines ask the person to switch with the model menu next to the message box (in the terminal, `/model <chat model>`) when the chat is known to be on another model; the summary, shown once per save, also says it when the model is not known at the start;
- a switch to another model is refused (`PreModelSwitch`), and the person reads why and that "change zero-touch settings" changes the chat model for new chats. A switch to the chat model always passes, and a switch whose target the hook cannot read is never refused: a guard that misreads its input must not lock anyone out of their model picker;
- a receipt from a hand-off made before the switch was seen still adds `This chat is on <model>, not <chat model>: …` to its line.

### A hand-off, step by step

The hand-off tools are the `mmo` server's (`plugin/mcp/model-dispatch/src/handoff/`). The server lists them only where a Hand-off chat can use them: when zero-touch is installed and switched on and its saved mode is Hand-off or not chosen yet (`handoff/listing.ts`). With every kind of work kept in the chat, only `undo_hand_off` is listed (an earlier landing can still be taken back), and handing a kind off later adds the other three. After the person leaves Hand-off mode (Workflows or Off saved), `undo_hand_off` alone stays listed while any chat's records hold a hand-off that is not fully undone. The undo then works from any chat outside a running workflow, a chat with no zero-touch record included: `plugin/hooks/ambient.sh` and `hook.mjs` let the undo's two moments through, the hook stamps it with its own line (`Zero-touch: taking back the hand-off you asked to undo.`), and the server accepts a stamped undo from any chat (`handoff/chat.ts`, `needRoutes: false`); the landing is found in any chat's records of the same project. Zero-touch's settings file it cannot use (damaged, or a mode it does not know) follows zero-touch's own fail-safe rule: the last good save decides, and with none zero-touch is Off, so they are not listed. When Claude Code's own record of installed plugins cannot be read, they are listed only if zero-touch has a data folder (it has run here); a developer's clone or `--plugin-dir` setup without zero-touch lists none. Claude Code does not tell a server which chat it serves, so the server reads what Claude Code and zero-touch keep on disk; if the saved mode later becomes Hand-off, the server adds the tools and tells Claude Code, which lists them again at once. They are never taken away while the server runs. Their descriptions are about 1,600 tokens, which no other chat carries. A call works only in a hand-off chat.

1. **The chat's model fills in the tool's form and makes one call.** The form is a brief, never the finished text. (For a repeated change it first makes the change itself, in one file.)
2. **The hook stamps the call** (`pre-handoff`): the chat's id, the project folder, who pays for a Claude typist, and the call's own id, so an interrupted call can be told apart. The server takes nothing else about the chat from the call: the policy and the model for this kind of work are read from the chat's own records, so nothing the model writes in a call can choose them. A call with no stamp, or whose chat is not a hand-off chat, is refused, and so is a call for work the person keeps in the chat (the hook refuses it first, the server again). So is a call inside a workflow run.
3. **Code checks the form** before anything is sent. Every problem is listed at once, by field.
4. **The typist writes.** The ladder is the executor's: two attempts by the model the person chose for this work (the second with the reason the first was refused), then one by **the chat's own model** (the person's chat model, or the organisation's, so no model the person did not choose works on their project). A chat with no one chat model (an organisation's alias) keeps the policy's Claude model for it. A vendor or network failure waits and is not an attempt. A refused login (HTTP 401 or 403) skips that model's second attempt. Every call is billed and logged, failed ones included.
5. **Code checks the answer**, and only a checked answer reaches the project. Tests and a repeated change are also run, in a scratch copy of the project (below).
6. **The receipt** goes to the chat's model (status, who wrote it, attempts, cost, what was checked, what to do next), and the person sees one line (`post-handoff`):

| Outcome | Line |
|---|---|
| A file written by the chosen typist | `Zero-touch: docs/setup.md was written by Flash 3.8 and checked automatically. Estimated cost: $0.0041. To undo it, ask Claude to undo the hand-off of docs/setup.md (going back in the chat doesn't undo it).` (a hand-off's files are written by the server, so Claude Code's rewind does not take them back) |
| A regression test written before the fix (`fails_until_fixed`) | `… was written by Flash 3.8 and checked automatically. Its tests fail for now, as expected, until Opus 5 fixes the bug. …` (it must fail in the test copy, on one of its own cases) |
| Someone else created the file meanwhile | `Zero-touch: tests/cart.test.js was created by someone else while the hand-off was running, so nothing was written over it (estimated cost: $0.02). Opus 5 will ask you what to do.` (never written over, and not handed back to be written over) |
| The person stopped it | `Zero-touch: the hand-off of docs/setup.md was stopped, as you asked, and nothing was added to your project (estimated cost so far: $0.02).`, at their next message (Claude never reads the reply to a stopped call) |
| The typist failed, the chat's model wrote it | `Zero-touch: Flash 3.8 couldn't write docs/setup.md, so Opus 5 wrote it. It was checked automatically. Estimated cost: $0.10. …` |
| Every attempt failed | `Zero-touch: the hand-off of docs/setup.md didn't work (estimated cost so far: $0.01), and nothing was added to your project. Opus 5 will write it directly now.` (the file is handed back to the chat's model) |
| The Claude sign-in this computer uses has expired (a hand-off to a Claude model) | `Zero-touch: the hand-off of docs/overview.md didn't run: the Claude sign-in this computer uses for Sonnet 5 has expired, so nothing was added (estimated cost: $0.0000). To fix it, sign in again: in a terminal, run claude and type /login. Opus 5 will write it directly now.` |
| Tests that ran and did not pass | `Zero-touch: the new tests in tests/cart.test.js didn't pass in the test copy (estimated cost: $0.10), so nothing was added. Opus 5 will look at why: if a test was wrong, it fixes the test; if the code has a real bug, it tells you.` |
| A repeated change, landed | `Zero-touch: Flash 3.8 made the change in 3 files, and your project's check passed on a test copy. Estimated cost: $0.01. To undo it, ask Claude to undo the hand-off of a.js; all 3 files are taken back together (going back in the chat doesn't undo it).` (`no automatic check was available` when none was given; `2 files still need the change, and Opus 5 will do them.` when some targets failed) |
| A repeated change that failed its check | `Zero-touch: the change couldn't be repeated safely (your project's check failed on the test copy; cost: $0.01), so nothing was changed. Opus 5 will make the change directly.` |
| An undo | `Zero-touch: hand-off hm4ra was undone: 2 files are back as they were.` |
| An undo whose files all changed since | `Zero-touch: hand-off hm4ra wasn't undone, because its file has been changed since. Opus 5 will ask you whether to undo it anyway.` (only on the person's yes is it undone, corrections and all) |
| The brief was not complete | `Zero-touch: Opus 5's instructions for the hand-off were missing 2 things, so nothing was sent and nothing was charged. Opus 5 is fixing them and will try again.` (a second refusal for the same file, or a command whose program is missing: `… couldn't be handed off, so nothing was sent and nothing was charged. Opus 5 will write it directly.`) |
| Any other refusal | `Zero-touch: this couldn't be handed off here, so nothing was sent and nothing was charged. Opus 5 does it directly.` (never the server's own reason, which Claude reads in the reply) |

Every hand-off that changes the project is one **landing** with an id on its receipt, recorded with what each file held before (`handoff/landing.ts`). An id is `h` and four letters or digits nobody misreads (`h7k2q`), unique among every chat's landings, so an undo asked in any chat, or after `/clear`, finds the right one.

**Stopping a hand-off.** When the person presses Stop, Claude Code cancels the call: the server stops the hand-off (no further attempt or wait, a running typist's program and a test command in the scratch copy are ended), writes nothing into the project, and hands the file back. Claude Code may not tell the server; so the `handoff-failed` hook (`PostToolUseFailure`) also marks the interrupted call by its id, and the server reads that mark just before anything is written. Either way the person reads the stopped line at their next message.

### `write_document` (docs, spec, plan)

The form (`handoff/document.ts`):

| Field | Holds | Checked |
|---|---|---|
| `kind` | `docs`, `spec` or `plan` | one of the three |
| `file` | the NEW file, from the project folder | inside the project (symlinks followed), not under `.git`, and not there yet: a change to a file that exists is the chat model's own edit |
| `purpose`, `readers` | what the document is for; who reads it | filled, one line |
| `sections` | each `heading` and `must_say` | at least one; no heading twice; every string one line |
| `facts` | everything the document may state about the project: each `statement`, its `source` (a project file, or `chat` for something the person said) and, for a file, a `quote` | at least one; a file source exists; **the quote is in that file word for word**; a fact from the chat has no quote |
| `style_from` | optional: a document whose tone and layout to follow | a file of the project |

Every string is one line: a field holding several lines or a code block is the finished text, which would mean the chat's model did the typing and the hand-off saved nothing. The typist is told it cannot see the project and may state only the facts.

The answer's checks refuse only what is certainly wrong whatever the document is about:

- a listed section has no heading of its own (in Markdown a heading line, so "Installation notes" is no "Install" section);
- a shell command is not one of the facts (commands joined with `&&` or `;` are each checked; a labelled shell block is commands throughout, an unlabelled block only where a line carries a `$` prompt);
- inline code naming a path under one of the project's own top-level folders, or a relative link, leads to nothing in the project. A word with a slash that is no project path (`text/html`) is left alone.

Whether the prose is right is the chat model's reading of the written file, which the receipt asks for.

### The scratch copy (`handoff/scratch.ts`)

Tests and a repeated change are **run** before they reach the project, in a copy of it, with a command the chat's model names in the form. The project is never the place a hand-off is tried out.

- The copy holds the project's own files as they are on disk now (tracked files and new ones, uncommitted work included) as real copies, copy-on-write where the file system has it, so whatever the command writes over them stays in the copy.
- What git ignores (installed dependencies, build output, caches) is linked in, not copied: it can be large, and the command needs it. A command that writes inside such a folder (a cache under `node_modules`) writes to the real one, as it does when the person runs it.
- Git is what tells the two apart, so **a project that is not a git repository gets no copy and the hand-off is refused**; the chat's model does the work itself. Nothing is written into the repository to make the copy (no commit, no worktree).
- The command runs through `sh -c`, as typed, with `CI=1` (runners do not wait for a person), both output streams together; the end of a long output is kept (8,000 characters, a stated bound). A command past ten minutes is stopped, its process group with it.
- **The command is the chat model's, run with the person's own rights**, as when the model runs it with Bash; Claude Code's permission prompt for the tool call shows it (the tests and repeated-change tools keep that prompt; only a new document and an undo, which run no command, are let through without it, below). Before anything is sent, the form check asks the shell that its program exists, and for `npm run <script>` / `npm test` that package.json has the script.

### `write_tests_from_cases`

Deciding what to test is judgment; typing the test file is not. The form (`handoff/tests.ts`):

| Field | Holds | Checked |
|---|---|---|
| `file` | the NEW test file | inside the project, not there yet |
| `target` | the file under test | a file of the project; its text travels with the brief |
| `functions` | the names the tests exercise | at least one; each is in the target as a whole name |
| `cases` | each `name`, `given`, `expect` | at least one; no name twice; every string one line |
| `style_from` | optional: a test file to follow | a file of the project; its text travels with the brief |
| `test_command` | the command that runs the new file | its program is on the machine; an npm script exists; no part of it is a command the person's Claude settings forbid (below) |
| `notes` | optional | one line |
| `fails_until_fixed` | optional: true for a regression test written before the fix of the bug it shows | the file must then FAIL in the scratch copy, and its failure must name one of its own cases (a file that does not even run names none); the receipt tells Claude to make it pass with the fix |

The answer is checked in two steps: every case has a test with exactly its name (however the file quotes it), then the file is written into the scratch copy and the test command runs there. **Only a file whose tests pass is written into the project.**

**A case's expected result is the specification.** The typist is told never to change it, or weaken an assertion, to make a test pass. So when the code under test does something else than a case expects, the tests keep failing, nothing is written, and the chat's model gets the run's output: a wrong case it corrects and hands off again; a real bug it tells the person. A hand-off that bent the tests until they passed would hide exactly the bugs tests exist to find.

### `repeat_edit_across_files` and `undo_hand_off`

**A hand-off's command and the person's Bash rules.** The model server runs `test_command` and `check_command` itself, in the test copy, where Claude Code's own rules for its Bash tool never apply. So `pre-handoff` reads the person's Bash deny rules (managed settings, `~/.claude/settings.json`, the project's `.claude/settings.json` and `.claude/settings.local.json`; the forms `Bash`, `Bash(cmd)`, `Bash(prefix:*)` and `*` wildcards, each part of a command joined by `&&`, `||`, `;`, `|` or a new line checked on its own; `lib/bash-rules.mjs`) and refuses a call whose command one of them forbids: `Zero-touch: this hand-off wasn't run, because the command it would run to check the work is one your Claude settings don't allow. Claude does the work in the chat instead.` Not covered, and said here: Claude Code's sandbox does not apply to a server's commands, and an "ask" rule is not asked by this check; the tests and repeated-change tool calls themselves keep Claude Code's own permission prompt, which shows the command.

**No permission prompt for a new document or an undo.** In Claude Code's default "ask" mode, every hand-off call would bring Claude Code's own prompt, showing the call's raw form (the stamp included) in words the person cannot judge. The person chose Hand-off, so `write_document` and `undo_hand_off`, which run no command, are allowed by `pre-handoff` with one line, `Zero-touch: handing this work off, as your Hand-off settings say. It is checked before anything reaches your project.` A deny or ask rule in the person's settings that names the tool (the server, the tool, or a `*` pattern, in the same four settings files) leaves the decision to Claude Code (`toolRuleFor` in `lib/bash-rules.mjs`). The two tools that run a command keep the prompt.

The chat's model makes a change **once, by hand**, in one file. The form (`handoff/repeat.ts`): `example` (that file; it must differ from the last commit, and its diff is the pattern), `targets` (the files to repeat it in), `change` (the change in words) and `check_command` (optional but wanted: the project's build or test command).

Each target is one job, a few at a time, answered as exact edits. Code checks each answer before any file is touched:

- every edit's search text is in the file exactly once (the executor's own rule), so an edit lands where it was meant or not at all;
- **an edit removes only lines the change is about.** The words the example's change took away (in its removed lines and in none of its added ones: `getUser` for a rename to `fetchUser`, `moment` for a move to another library) mark such a line. An edit that removes a line carrying none of them is rewriting something else and is refused. A change that only added lines took no word away, so its repeats may add lines and remove none. A line that only changes its indentation is not removed.

Then every changed file is written into the scratch copy (which already holds the example as changed) and the check command runs there. When it passes, the files are written into the project as one landing; when it fails, nothing is changed and the output comes back. A target whose edits never pass is named back to the chat's model, which changes that file itself; the others still land. A file that needs no change is reported unchanged. Just before landing, every file is read again: if one changed in the project while the hand-off ran (the person in their editor, another chat), nothing lands and the person reads why, because the edits were made against the old text and the check ran on all of them together (documents and test files are new files, and one that appears meanwhile is never overwritten either).

`undo_hand_off` takes a landing back by its id, or by a file it wrote (that file's latest hand-off, `handoff/landing.ts` `landingIdForFile`): a file it changed gets its earlier text, a file it created is removed. A file that no longer holds what the hand-off wrote was changed since (often Claude's own correction, which the receipt asks for); it is left alone and named. Undo is kept per file, so a partial undo can be finished. When every file of the landing changed since, nothing is undone and the landing stays; Claude asks the person, and only on their yes calls again with `include_changed: true`, which undoes it, corrections and all. An undo asked in another chat, or after `/clear`, finds the landing in the chat that made it, for the same project only. A landing can be undone while that chat's records are kept: 30 days after the chat was last used (the sweep, in "What is stored, and where").

## What zero-touch leaves alone: every `/mmo:` command

Zero-touch sits on top of the pipeline and changes nothing the pipeline does. That covers every `/mmo:` command, typed or started by routing: the same phases, gates, policies, routing, typists, worker launches, output caps and hooks of its own.

**With zero-touch off (the plugin disabled or not installed), the `mmo` plugin is the pipeline alone:** no zero-touch hook is registered at all (they are the zero-touch plugin's), and the server does not list the four hand-off tools (`handoff/listing.ts` hides them when zero-touch is not installed, switched off, set to Workflows or Off, or plugin hooks are switched off).

**With zero-touch on, a typed `/mmo:` session sees none of it:** from the `/mmo:` prompt on, zero-touch stands down until the run ends, and the pipeline's own agents get their explicit tool lists. One thing differs, in ordinary chat only: which workflow the chat's model may start by itself. Without zero-touch it may start any; in workflow mode only the one the rules recognised in the person's message (Guard B); in hand-off mode none. Which workflow may start changes; how a workflow runs does not.

**What zero-touch changes in the pipeline's own files.** Zero-touch is an add-on: a typed `/mmo:` run behaves as mmo does without zero-touch, with every shipped policy, zero-touch on, off, disabled or not installed; a run zero-touch started uses mmo's own helpers on the chat's model (above). mmo's command, skill and agent texts say nothing about zero-touch (`tools/test/zero-touch-workflow-tag.test.mjs` holds them to it). The one change to them holds for every run:

- **Where the commands, the brownfield manual and the orchestrator's instructions point the model.** They name their files by the installed plugin's own path, `${CLAUDE_PLUGIN_ROOT}/…`, which Claude Code fills in with the plugin's real folder in commands, skills and agents, so a model that follows a path literally finds the file on an installed plugin (a path inside this repository, such as `/plugin/skills/brownfield-guide/SKILL.md`, exists only in a clone of it). Links to the repository's own `SETUP.md` and `docs/`, which an installed plugin does not carry, name `/mmo:setup` or `/mmo:policy` instead. What the files say is otherwise unchanged (`tools/test/plugin-paths.test.mjs`).

The version notes ([methodology.md](methodology.md)) list it with mmo's other fixes.

## After a Claude Code update

Zero-touch relies on these behaviours of Claude Code, and an update can change any of them silently. A version in brackets is the Claude Code version that behaviour was verified on.

- **Routing:** a note the prompt hook adds reaches the model; a `UserPromptSubmit` block keeps a typed command from the model and shows the person the reason; a `PreToolUse` deny on the `Skill` tool stops a command and the model reads the reason; a message typed while Claude works is recorded in the transcript as a `queued_command`, and every message as `queue-operation` entries (enqueue, then dequeue or remove); every hook gets `CLAUDE_PID` (the chat's Claude Code process; the project lock follows it) and `CLAUDE_CODE_SESSION_ATTENDED` ("0" for a run nobody attends, such as a `claude -p` started from inside a chat); the desktop app's /clear is the app's own (it ends the chat's Claude Code process and starts a new chat; no SessionEnd "clear" is sent, which only the terminal's /clear sends); both plugins' `SessionStart` hooks run for a new chat and after `/clear`, and a start hook's `systemMessage` is shown to the person in the terminal (not in the desktop app, which shows a message hook's line instead, collapsed; the desktop app runs hooks with `CLAUDE_CODE_ENTRYPOINT=claude-desktop`); a multiple-choice answer reaches `PostToolUse` as `answers[<question>]`; a `Stop` hook's `additionalContext` reaches the model and continues the turn; and `${CLAUDE_PLUGIN_ROOT}` is filled in inside commands, skills and agents.
- **Hand-off mode:** a start hook's `additionalContext` reaches the model, at a fresh start and after a compaction; a `PreModelSwitch` deny stops a model switch and the person reads the reason; the start moment or the transcript names the chat's model; a `PreToolUse` hook's `updatedInput` replaces the input of one of the plugin's own server tools (the hand-off stamp, and the workflow policy stamp); and a `PostToolUse` hook's `systemMessage` is shown after such a tool answered.
- **The settings box:** a `PreToolUse` hook fires on `AskUserQuestion` before the box is shown, and its deny keeps the box from the person, with the reason reaching the model; the clicks reach `PostToolUse` as `tool_response.answers[<question>] = <label>`; a closed box reaches no hook; a run with no screen is labelled `CLAUDE_CODE_ENTRYPOINT=sdk-cli` (a run started from inside another Claude chat inherits that chat's label); `${CLAUDE_PLUGIN_DATA}` reaches the plugin's hooks; and the `PreToolUse` hook's `updatedInput` replaces the box.
- **The `/clear` fix:** `/clear` fires `SessionEnd` with reason `clear` for the old chat id, then starts the cleared conversation under a new id.

After every update, in one new chat with zero-touch on: the start lines show (the terminal at the start, the desktop app with the first message); "change zero-touch settings" opens the exact box and a click is saved; a clear job message starts its workflow; a second job asked for in plain words during it is queued and said, and a typed `/mmo:` workflow command during it gets the Queue-or-Replace question; and a `/mmo:` command the chat tries by itself is refused with its reason. `tools/test/ambient-routing-hooks.test.mjs` proves the plugin's side; the live chat proves the app's.
